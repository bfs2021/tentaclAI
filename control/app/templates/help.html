Getting started

  1. Settings: check paths, domain, git name/email and the remote control name.
  2. Overview → Create & start (or “Apply now” if the container already runs).
  3. Overview → Sign in now (terminal “Claude login”, claude auth login): open the link, sign in with your claude.ai account, paste the code into the terminal.
  4. Terminal → Claude · RC (remote control): confirm the prompts (e.g. trust the folder). The session then shows up in claude.ai/code and the Claude app.
  5. Tentacles → Services: connect your Docker hosts, APIs, MCP servers and repositories from templates, add tokens, then Test connection and Onboard with Claude.
  6. Overview → System inventory: Claude gets to know your site and records it in local/CLAUDE.md.

Site & installation

tentaclAI is generic – everything site-specific lives in a few places:

.envpaths (TC_DIR, DOCKER_SOCKET, HOST_DOCS, CA_CERT), domain, resources, remote control, tokens – editable under Settings.
services/*.jsoneverything Claude can reach: Docker hosts, APIs, MCP servers, git repositories, databases, web sources, files, mail.
compose.override.yamlreverse proxy (nginx-proxy, Traefik …), extra mounts, labels for container managers. Template: compose.override.example.yaml.
local/CLAUDE.mdrules and knowledge about your site for Claude; loaded together with the generic rules on every start. The host docs (HOST_DOCS) are only referenced – Claude reads them before it works on the host.

Install on a new host

git clone … tentaclai && cd tentaclai
./tentaclai.sh init                 # guided setup: paths, domain, access (port / nginx-proxy / Traefik),
                                      # git, remote control, limits – then starts tentacontrol
./tentaclai.sh init --defaults      # the same without questions

Without a reverse proxy tentacontrol listens on http://127.0.0.1:8484 (CONTROL_BIND/CONTROL_PORT). For a public repository, .gitignore keeps .env, compose.override.yaml, local/, services/*.json, ssh/keys, ssh/config.d, data/ and workspace/ out; the *.example files are their templates.

How it fits together

Tentacles are everything Claude can reach – services, SSH hosts and the systems that group them – set up under Tentacles, each with its own access mode. Any other network traffic goes through the egress gateway (Network).

tentaclAIContainer with Claude Code, git, Python, Node, gh, database clients and svc – no Docker CLI or socket (docker runs on the hosts over SSH). It reaches only connected services – Docker hosts, APIs, MCP servers, git repositories, databases, web sources, files, mail.
tentacontrolThis web admin. Edits .env, services/, ssh/ of the stack and builds/recreates tentaclAI.
services/*.jsonOne file per service (parts: docker, api, mcp, git, db, web, files, smtp, imap). Tokens only as ${VAR}.
.envAll values and secrets (mode 600). svc reads it fresh on every call.
/workspaceProjects, SERVICES.md (generated service catalog), repos/ (git services).
data/claudeClaude's home (/home/claude, user claude): login, settings, history.
data/homeRoot's home in the sandbox (/root): svc state – git mirrors, caches. Claude can't read it.

Everything lives under {{ site.tc_dir }} – include it in your backups (especially data/, ssh/keys, .env).

Terminal & tmux

Every Claude terminal runs in a tmux session in the container. Closing the page or losing the connection does not end Claude – opening it again re-attaches.

The status line at the bottom of every Claude session shows that it runs in the sandbox, the model and directory, and – refreshed every 5 seconds – approvals waiting in Activity. It is set in ~/.claude/settings.json only if you have no status line of your own.

Ctrl+B then Dleave the session, Claude keeps running
mouse wheelscroll the history
drag, then Cmd+C / Ctrl+Shift+Ccopy – tmux selects and hands the text to the page (Safari needs the key press)
Shift + drag (Mac: Option + drag)select in the browser instead of tmux, e.g. outside tmux sessions
Ctrl+Shift+V / right clickpaste (e.g. a login code)
Ctrl+C twicequit Claude

On the host the same works with ./tentaclai.sh, in a container console (e.g. Arcane, Portainer) with cc.

Remote control

The tmux session claude-rc runs claude remote-control permanently; when it ends it restarts after a delay. Requirements: Claude signed in with a claude.ai account (an API key is not enough) and a one-time confirmation in the terminal.

Other account: Overview → Claude Code → Sign out ends the login of the sandbox (the card shows which account is signed in) and restarts remote control; then Sign in now with the other account. Running Claude sessions stop working until then.

RC_ENABLEDon/off
RC_NAMEsession name in claude.ai/code and the app
RC_WORKDIRstart directory (e.g. /workspace or a stacks directory)
RC_EXTRA_ARGSextra arguments for claude remote-control
RC_RESTART_DELAYdelay before restarting (seconds)

The values are read fresh on every start of the session: change them under Settings, then press “Restart” on the remote control card – no container recreate needed.

Services

A service is one JSON file in services/. It can have nine parts – alone or combined (db, web, files and mail have their own sections below):

dockerDocker host – reached over SSH (this host too); Claude manages its stacks with svc docker / svc compose.
apiREST API, called with svc <name> GET /path. svc injects the authentication; tokens never appear in commands.
mcpMCP server – registered in Claude's configuration on “Sync”.
gitRepository – cloned to /workspace/repos/<name>, read only or read/write.
db · web · filesDatabase (svc db), web pages as text (svc web), directories on an SSH host (svc files).
smtp · imapSend mail, read a mailbox (svc mail).
  • Test path ("test_path"): the endpoint svc test calls for the API – pick one that needs the token, so a wrong token shows up. Without it GET / is used; the service page warns and suggests the template's path (Save as test path).
  • Rename on the service page: the file, svc <name> calls in examples and notes, and for git services the mirror and /workspace/repos/<name> move together; tokens, system and rules stay.
  • Token variables: a second service from the same template gets its own variables (<NAME>_…) instead of sharing the first one's tokens. If services do share a variable, the Tokens & variables card says so.
  • Template addresses use the placeholder example.com – the service page reminds you as long as it is there.

Structure

{
  "name": "paperless",
  "description": "Paperless-ngx – documents",
  "api": {
    "base_url": "https://paperless.example.com/api",
    "auth": { "type": "header", "header": "Authorization", "value": "Token ${PAPERLESS_TOKEN}" },
    "insecure_tls": false,
    "docs": "https://docs.paperless-ngx.com/api/"
  },
  "mcp": { "type": "http", "url": "https://…/mcp", "headers": { "Authorization": "Bearer ${PAPERLESS_TOKEN}" } },
  "test_path": "/documents/?page_size=1",
  "examples": ["svc paperless GET /documents/?query=invoice"],
  "notes": ["Read only unless explicitly asked"]
}
  • Status: active all variables set · token missing at least one ${VAR} empty · disabled "enabled": false.
  • New tokens work for svc immediately. Only settings read at container start (e.g. GIT_*, TZ, resources) need “Apply now” – the banner also appears when a newer tentaclAI image was built.
  • Running Claude sessions see new MCP servers after /mcp → reconnect or in a new session.
  • Internal https services with your own CA: set CA_CERT in the settings – the CA becomes trusted in the container. Single devices with self-signed certificates: "insecure_tls": true.
  • Self-signed certificates (routers, NAS, hypervisors): the switch Ignore TLS certificate errors on the service page sets insecure_tls for its api, web, git, db, smtp and imap parts – encrypted, but the server is not verified. MCP connections are made by Claude Code and always verify; use CA_CERT for them.

Docker hosts

Docker management is a service like any other, always over SSH – the sandbox never gets a Docker socket. Template: “Docker host (SSH)”.

"docker": { "mode": "ssh", "ssh_host": "vps1", "stacks_dir": "/opt/stacks", "access": "ro" }
  • ssh_host: alias from Tentacles → SSH hosts; the user there must be allowed to run docker (or sudo it – sudo prefix on the SSH host). Docker and compose run on that host, compose in the stack's directory. This host: an SSH host with hostname host.docker.internal.
  • access: ro only allows read-only commands through svc (ps, logs, inspect, config …); rw allows changes – Claude asks before restarts, updates and deletions.
  • Commands: svc docker (overview), svc docker <host> ps, svc compose <host> <stack> logs --tail 50.

Onboarding a service

On every service page: Test connection checks each part (API test call, MCP reachability, git ls-remote, docker version, database and web login, SMTP/IMAP login) – in the container: svc test <name>.

Onboard with Claude runs /onboard <name>: Claude tests the service, explores it read-only (docs/OpenAPI, a few queries, repository content, stacks), asks you what it is for, typical tasks and what is allowed or off limits, and writes description, rules and examples into the service file after your approval. That way the catalog says what each service is for.

Databases db

PostgreSQL and MySQL/MariaDB with a direct connection (templates “PostgreSQL database”, “MySQL / MariaDB database”). User and password come from .env; svc passes them only via environment or a 0600 file, never on the command line.

"db": {"engine": "postgres", "host": "db.lan", "port": 5432, "database": "app",
       "user": "${APP_DB_USER}", "password": "${APP_DB_PASSWORD}", "ssl": "prefer", "access": "ro"}

Claude: svc db <name> "<SQL>", tables, describe <table>, --csv; shell only for rw. With ro the session is read-only and statements that would switch it to read-write are refused – the real protection is still a read-only database user (see the template's setup hint).

Web sources web

Websites to read from – wikis, intranet pages, documentation. Auth: none, basic, bearer, header or form (login form with cookie, optional hidden CSRF field). Only URLs on the configured host are fetched; paths can restrict it further.

"web": {"base_url": "https://wiki.lan", "auth": {"type": "form", "login_url": "/login",
        "fields": {"username": "${WIKI_USER}", "password": "${WIKI_PASSWORD}"}, "csrf_field": "_token"},
        "paths": ["/wiki/"]}

Claude: svc web <name> <path> returns the page as readable text with links, --links lists the links, --raw the HTML, --login logs in again. Read-only; page content is treated as data, not instructions.

Mail smtp / imap

Sending (smtp) and reading a mailbox (imap) – one part or both in one service. Like databases, mail goes through the egress gateway (svc tunnels it); security is starttls, ssl or none (an internal relay), the port follows from it unless set. Templates: SMTP relay (no login), SMTP (with login), Mailbox (IMAP + SMTP).

"smtp": {"host": "smtp.example.com", "security": "starttls", "user": "${MAIL_USER}", "password": "${MAIL_PASSWORD}",
         "from": "tentaclai@example.com", "recipients": ["@example.com", "boss@example.org"], "access": "confirm"},
"imap": {"host": "imap.example.com", "security": "ssl", "user": "${MAIL_USER}", "password": "${MAIL_PASSWORD}",
         "folders": ["INBOX", "Alerts"], "access": "ro"}
  • smtp: confirm (default) – every mail waits for your approval, showing recipients, subject and the start of the text. rw sends without asking and only works with a recipients list (addresses or @domain, exact domain); if a list is set it also limits confirm. ro doesn't send.
  • imap: ro (default) lists and reads – reading uses a read-only mailbox and doesn't mark mails as seen. rw / confirm also mark (seen, flagged) and move between folders (only on servers with IMAP MOVE – nothing is ever deleted). folders limits what Claude sees.
  • Mails are untrusted content: anyone can write to a mailbox. svc mail … read puts the text between unmistakable markers, and Claude's rules say never to act on instructions in a mail. Together with confirm and a recipient list on smtp this keeps a planted mail from sending your data away.

Claude: svc mail <name> send --to a@x --subject "…" --body-file F (or the text from stdin), folders, list [FOLDER] [--unseen] [--from X] [--subject X] [--since YYYY-MM-DD] [--limit N], read <uid>, flag <uid> seen|unseen|flagged|unflagged, move <uid> <folder>. svc test connects and logs in without sending or changing anything.

Directories & files files

A directory or file on an SSH host – e.g. a local repository or a config folder – without a bind mount. ssh_host may be left empty when the service belongs to a system with an SSH host; sudo: true uses that host's sudo prefix.

"files": {"ssh_host": "nas", "path": "/srv/config", "access": "ro", "sudo": false}

Claude: svc files <name> ls|tree|cat|grep [path] reads on the host; pull [path] copies into /workspace/files/<name>/, diff shows what would change and push writes back (rw only, no deletions). Paths are relative to the service path, .. is refused.

Git repositories

"git": {
  "url": "https://github.com/OWNER/REPO.git",     // or git@github.com:OWNER/REPO.git (SSH)
  "access": "ro",                                   // ro = read only, rw = commit + push
  "branch": "main",                                 // optional
  "path": "/workspace/repos/REPO",                  // optional, default /workspace/repos/<name>
  "auth": { "type": "token", "token": "${GH_TOKEN}", "username": "x-access-token" }   // or { "type": "none" }
}
  • ro: push is blocked twice (blocked push URL + pre-push hook). Ideal for public repositories or third-party code as reference.
  • rw: Claude may commit and push – when you ask for it.
  • Tokens never end up in .git/config: a credential helper (svc git-credential) reads them from .env when needed.
  • SSH URLs use the tentaclAI key – add it as deploy key in the repository (see Tentacles → SSH hosts).
  • Cloning happens on sync or with the “Clone” button; “Fetch” pulls changes and re-applies ro/rw.
  • Usernames per provider: GitHub x-access-token, GitLab oauth2, Gitea/Forgejo any.

System inventory

This is how Claude gets to know a new site. Start: Overview → System inventory, terminal tab “System inventory” or ./tentaclai.sh inventory.

  1. tc-scan collects read-only for every docker host (over SSH): system (OS, Docker, resources), all stacks and containers (images, status, ports, proxy hosts, mounts), networks, connected services with a test call, git repositories and the SSH hosts. Environment variables and .env contents are never read.
  2. Claude summarizes and asks short rounds of questions: purpose and criticality of the stacks, taboos, container manager, proxy/DNS, backups, access, conventions.
  3. Claude shows a draft for local/CLAUDE.md and writes it only after your approval (with a backup copy).

Report only: ./tentaclai.sh scan or tc-scan in the container. The inventory can be repeated at any time – existing knowledge is kept.

Systems

A system groups the services that belong to one host or appliance – e.g. the SSH access, the docker host and the API of the same server. It has a description, an optional SSH host and rules that apply to every member. Services join with "system": "<name>" in their JSON (set it on the system's page under Services); services without a system stand alone.

  • Files: systems/<name>.json (example: systems/_example.json).
  • Docker services of mode ssh without their own ssh_host use the system's SSH host.
  • claude.ai connectors (Google Drive, Claude Docs …) come with your Claude account and reach the outside directly, not through svc. They appear as built-in tentacles at the end of the Services page and are off by default; switched-off connectors are denied in the sandbox's managed settings (root-owned).
  • A service is only needed for credentials or write access – public, read-only sources (docs, registries, public repos, websites) just need an entry under Network → Allowlist; Claude uses them directly.
  • Rule of thumb: one service = one way in with one set of credentials (an API and its MCP server may share a file); one system = one machine or appliance.
  • Claude sees systems in the service catalog and via svc systems [name]; svc info <service> also prints the system's rules.

Activity: approvals & audit log

Parts with an access field (api, docker, git, db, files, smtp, imap) have three modes:

  • ro – writes are refused (and logged as blocked).
  • rw – writes run and are logged (auto). Default for api.
  • confirm – every write waits for you: Activity shows the request with a badge in the sidebar, Approve runs it, Deny or no answer within 10 minutes stops it. Approve + 15 min also lets further writes of the same service part (or SSH host) run for 15 minutes without asking – listed under Active grants, revocable any time, gone when tentacontrol restarts; never for svc config put. Claude is told to report a pending approval and never to work around a denial.
  • Every approval and audit entry shows where it came from – the Claude session (Remote Control, a terminal, onboarding …) and its title, or Job · name for a scheduled job (recognised by svc, not reported by Claude). Pending approvals also show as a banner on every page. Claude's own environment reports it, so take it as a hint, not as proof.

Writes are: API calls other than GET/HEAD/OPTIONS, docker/compose commands that change something, SQL that is not a plain query (and the SQL shell), svc files … push, sending mail and marking or moving mails, and git push (via a pre-push hook in every repo). The audit log (data/control/audit.jsonl) records time, service, action, decision and result – never tokens or request bodies. In the sandbox: svc audit.

Also gated: svc ssh <host> … (per SSH host, default confirm; plain status commands run without approval, even on ro hosts: uptime, df, free, ps, ls, docker ps|logs|inspect …, systemctl status|list-units …, journalctl, ip a|route, ss and similar – no shell syntax, no file contents, optionally behind the host's sudo prefix) and svc config put … – Claude's way to write a service file or local/CLAUDE.md, which always needs your approval.

Claude runs as the unprivileged user claude and can't read .env, the SSH key or the audit log, nor change service files – svc (root, via sudo) is its only way out. MCP tool calls are not gated (Claude Code asks for them itself); MCP servers with tokens run through svc mcp-proxy.

Network

All traffic of the sandbox leaves through the egress gateway; Network shows and controls it.

Mode

How the gateway treats a destination that no rule covers. permissive (default): allowed and recorded – use it to learn what the sandbox needs. enforce: held for up to 60 s while you decide in Activity (Allow 10 min, Allow 1 h, Always, Deny, Block); refused if nobody answers. EGRESS_MODE in .env.

IP targets

Connections to a bare IP address instead of a name (curl https://93.184.215.14). Normal programs almost always use names, so in enforce mode such a connection without a rule is blocked (block, default) or asked about like any other unknown destination (ask). In permissive mode it is allowed like everything else. EGRESS_DIRECT_IP in .env.

Rules

Checked in this order: Built-in (Anthropic, GitHub, PyPI, npm – always allowed, can't be blocked) → Blocklist (always refused, even for tentacles) → your allowlist (added here, with Allow on a seen destination, or Always in Activity) → tentacles (hosts of your active services and SSH hosts, derived live) → temporary approvals. Entries: host, *.domain (subdomains only), an IP or a range like 10.0.0.0/8, each optionally with :port. The gateway resolves names itself and checks IP rules against the resolved address, so a blocked range can't be reached through an allowed name. Seen lists every destination with its rule and last result.

Jobs

Jobs run Claude tasks on a schedule – reports and checks such as patch status, certificate expiry, disk space or last night's backups (templates for these are offered). Clone copies a job (the copy starts paused). A job is a task, a schedule (every hour, daily or weekly at a time, every N hours, a cron expression, or manual – then it runs just with Run now), a profile and a notification rule. Each run is a fresh Claude session with a 20-minute limit (adjustable); only one run at a time, a run that is still going skips its next turn, a run missed while tentaclAI was down is made up for if it is at most 6 hours old, and runs are skipped while a plan limit is at 90 % or more. Claude answers with a traffic light – ok, warn or alert – plus a title and a summary; by default you only hear about warn, alert and failures, and the badge next to Jobs in the sidebar counts the ones you haven't looked at (events Job finding and Job failed in Notifications).

Naming tentacles: write @name in the task (the editor completes service and SSH host names). Saving checks that they exist and warns when something won't work – a disabled service, sending mail from a read-only job, a confirm tentacle whose approval nobody gives at night. Claude gets a line about each named tentacle, so it doesn't search the catalog first. With Only the tentacles named in the task the run may use nothing else: svc refuses every other service and SSH host, and MCP servers are off (their tools would reach services past svc) – least privilege for a job that, say, reads mail. While a run is going its row shows a spinner, the running time and Claude's steps live – each tool call (e.g. the svc command), its output and Claude's text; the page reloads by itself when it ends. Finished runs keep their steps under Claude's steps – the quickest way to see why a job reported warn.

Proposing instead of acting: with Propose actions (read-only profile) the run only analyses and returns proposed changes – each a title and exactly one svc command (no pipes, ; or $, no svc config; others are shown as refused). The run lists them right below its row with check boxes for 24 hours, and the badge next to Jobs counts them (pulsing, like approvals); Discard selected / Discard all drop proposals you don't want; Run selected runs exactly the picked commands through svc, without Claude – ro stays ro, a confirm tentacle asks for approval as usual (the banner shows it right away), and a job limited to its named tentacles stays limited. Example: a spam check proposes svc mail box move 912 Junk at night, you pick it in the morning – no approvals at 3 a.m.

From the terminal: svc jobs lists the jobs, svc jobs <name> [--runs N] [--steps] shows a definition (as JSON) with its recent runs and, with --steps, Claude's steps – so you can ask Claude why a job reported warn and have it tune the prompt. svc config put job <name> <file> creates or changes a job: tentacontrol checks it with the editor's rules first, then it waits for your approval in Activity (preview: schedule, profile, start of the task); a new job starts paused – switching it on stays here. A running job can't create or change jobs.

{"name": "Mail test", "prompt": "Send a test mail via @mailrelay …", "schedule": {"kind": "daily", "time": "07:00"},
 "profile": "standard", "scope": true, "notify": "findings", "model": "haiku", "max_minutes": 5}

The profile is the job's limit on top of each tentacle's own access – the stricter one wins. read-only (default): every tentacle counts as ro, files in the sandbox can't be edited and MCP tools are off. Two layers enforce it: Claude Code only allows reading tools, svc and a few text tools for pipes (svc … | grep … | head – Settings → Jobs, default echo, head, tail, grep, jq, sort, uniq, wc, cut, tr, date, sleep; shells, interpreters, awk/sed/find/xargs and network or write tools are refused), and svc itself recognises the run (by a marker on the run's wrapper process and root's list of running jobs) and refuses every write – a marker Claude makes up can only make it stricter. standard: like a terminal session – confirm tentacles wait for your approval in Activity (shown as “Job · name”; it expires after 10 minutes and the job reports that), rw tentacles are written without asking; the editor lists them.

SSH targets

tentaclAI has its own key (ssh/keys/tentaclai_ed25519). Each host is a Host block in ssh/config.d/. Everything works in the UI:

  1. Add host – alias, host, user, port, optionally a jump host (ProxyJump through another SSH host) and sudo.
  2. Confirm the host key – tentaclAI fetches it and shows the fingerprint; compare it with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the host.
  3. Authorize tentaclAI – enter the user's password once (passed to sshpass via stdin, never stored or logged), or add the key by hand with the shown command.
  4. The host is saved and tested (login, sudo).

Edit changes host, user, port, jump host, sudo and the alias – a rename also updates docker/files services, systems and other hosts that jump through it. If a host key changed, Check host key fetches and confirms the new one. Remove can also take tentaclAI's key off the host. On the command line: ./ssh-host.sh list|add|sudo|hostkey|remove|test – same logic as this page.

Hosts without root login: sudo

If the SSH user is not root, enable use sudo (when adding the host, or later in the sudo column). The prefix (default sudo -n, also e.g. doas) is stored as # tentaclai: sudo=… in the host's block. svc docker/svc compose and tc-scan use it automatically, and Claude's instructions list it per host for admin commands.

It is non-interactive: the user needs passwordless sudo, ideally limited, e.g. /etc/sudoers.d/tentaclai: deploy ALL=(root) NOPASSWD: /usr/bin/docker. “Test” checks login and sudo.

Claude

Everything that steers Claude in the sandbox, in one place. Changes apply to new Claude sessions.

Instructions

Instructions shows how Claude's instructions are put together: in every session Claude reads ~/.claude/CLAUDE.md, generated at every start and sync from the base rules (image), the host tables (from your tentacles) and an import of your site rules (local/CLAUDE.md). When needed it looks up the rules of a service or system (notes, shown by svc info / svc systems), the service catalog /workspace/SERVICES.md and – for work on the host – the host documentation (HOST_DOCS). The site rules are edited right there (the previous version is kept as .bak-…); /inventory drafts them, and Claude can propose changes with svc config put local (always waits for your approval). The generated CLAUDE.md can be viewed, not edited. Service and system rules are edited on their own pages.

Memory

Memory lists what Claude noted for itself (~/.claude/projects/*/memory/): MEMORY.md is the index read in every session, the entries are opened when they matter. Deleting an entry also removes its line from the index.

Models

Models: Models sets the model and effort for every session (terminal and Remote Control), for subagents and for the set-up commands /inventory and /onboard – e.g. Sonnet for routine work saves plan quota. Standard leaves the choice to Claude Code. A fresh installation runs subagents and the set-up commands on Sonnet. Written as model, effortLevel and CLAUDE_CODE_SUBAGENT_MODEL into Claude's settings.json and into the commands' frontmatter; a /model switch inside a session only lasts for that session.

Skills

Skills of Claude Code and your account: Skills sets each one to On, /command only (only when you call /name) or Off – every skill Claude is offered costs context in every request. Those that make no sense in a headless sandbox (Office files, Artifacts, browser and computer use …) start off. Written as skillOverrides into Claude's settings.json; entries of your own for other skills stay. inventory and onboard are required by tentaclAI (its buttons start them) and can't be switched off – /command only keeps them working.

Usage

Usage shows the plan limits (session and week, account-wide) and what contributes to them – from Claude Code's /usage, asked every 10 minutes without a model call – plus tokens per day, the sandbox's sessions and the models used, read from the local session files (usage fields only, never the conversation). A quota notification goes out at 80 %.

settings.json

settings.json edits Claude Code's own settings in the sandbox – for everything without a page of its own (permissions, language, attribution, cleanupPeriodDays …; see the Claude Code settings). The parts other pages manage (skillOverrides, model, effortLevel, the subagent model and the telemetry switches) are left out and stay as they are; env values with secret-looking names are masked. The JSON is checked before it is written, the last 5 versions are kept as settings.json.bak-…. The managed settings (blocked connectors) are a policy Claude can't change and are not editable here.

Settings

Edits the stack's .env. Secrets are never shown – variables whose name looks like one (TOKEN, KEY, PASS, SECRET, AUTH, PAT …) and every variable a service uses as a credential (in auth, headers, password …) – leaving the field empty keeps the value, the “clear” checkbox removes it. Changes that need a new container show “Apply now” at the top (running sessions end); remote control changes only need “Restart” on the overview.

Notifications

Settings → Notifications: add channels (ntfy, webhook, e-mail – server, port, security, sender, recipients, optional login – or any Apprise URL – Telegram, Discord, Slack, Teams, e-mail, Home Assistant), send a test, and tick which event goes to which channel. Urgent events (approval needed, Remote Control down, signed out, container stopped) also come during quiet hours; the same event is sent at most once per dedupe interval. Channel URLs are stored in .env as NOTIFY_URL_….

Security

Settings → Security switches on two-factor sign-in: scan the QR code with an authenticator app (Google Authenticator, Aegis, 1Password, Bitwarden …), enter its code, keep the 10 recovery codes (each works once, for a lost phone). From then on tentacontrol asks for a code after the password; “Trust this browser” skips it for 30 days in that browser – the trusted browsers are listed there and can be revoked. Switching off needs the password and a code. No phone and no recovery code: ./tentaclai.sh reset-2fa on the host. A sign-in with a recovery code sends a notification.

Updates

tentaclAI releases: tentacontrol checks the GitHub releases every 6 hours (no token, nothing is sent except the request itself) and shows “Update available” in the sidebar; the Updates page lists the upgrade steps of the release. Update with ./tentaclai.sh update on the host – it shows the changes and upgrade steps, pulls, rebuilds and asks before recreating each container. Turn the check off with UPDATE_CHECK=false, point it to a fork with UPDATE_REPO (Settings → Updates).

Claude Code is installed when the image is built. “Update now” rebuilds the image (with a fresh base image) and recreates the container. Pin a version with CLAUDE_CODE_VERSION in the settings. tentacontrol itself is updated on the host: docker compose up -d --build control.

Security

  • tentacontrol has the Docker socket of this host (to run tentaclAI) – that is root on {{ site.hostname }}. Choose the tentacontrol password accordingly.
  • In tentaclAI, Claude runs as the unprivileged user claude. .env, the SSH key, the service files and the audit log belong to root; svc (via sudo) is the only way to services and enforces ro/rw/confirm. Client tools run as a third user (tcrun) with only their own secret.
  • Network: permissive records every destination, enforce asks for unknown ones – see Network.
  • tentacontrol is out of Claude's reach: from the sandbox only svc's endpoints for approvals and job proposals answer (with its token; an unrecognised address from the sandbox network counts as the sandbox) – the admin UI, the login and the gateway's endpoints refuse it, and only the gateway may use the latter.
  • Other services' secrets are blanked in free read-only output: docker … inspect, compose … config and systemctl show|cat show [redacted by svc] for values with secret-looking names and for passwords in URLs. Logs and commands you approve are not filtered. svc also keeps the .env values out of the environment of the programs it starts.
  • The sandbox sits in an internal network without a route to the outside; everything leaves through the egress gateway (tentaclai-egress), which records every destination. EGRESS_MODE=permissive (default) allows all – allow/block lists and approvals follow.
  • An rw docker service is root on that host. The sandbox itself never gets a Docker socket – docker hosts are reached over SSH only.
  • Login: bcrypt hash, optional two-factor sign-in (TOTP, see Settings → Security), 12 h session, SameSite=Strict cookie (Secure behind https), origin check for forms and the terminal, throttling after failed attempts (password and code).
  • Secrets never reach the browser; svc passes them to curl through temporary 0600 files on tmpfs, not on the command line.
  • Claude keeps asking before actions – the rules are in its instructions (generic rules + local/CLAUDE.md). Scheduled jobs run without prompts: read-only is enforced by Claude Code and svc, a job can be limited to its named tentacles, and confirm still waits for you – see Jobs.
  • Mails are untrusted: svc mail … read frames them between markers Claude never obeys; sending is confirm by default and rw only with a recipient list – see Mail.
  • Forgot the password: ./tentaclai.sh passwd on the host.

Troubleshooting

“token missing” although it was enteredcompare the variable name in the JSON and in .env (case sensitive).
API test returns HTTP 401/403wrong token or missing permissions; for header auth check the prefix (e.g. Token … vs. Bearer …).
TLS errorsown CA → CA_CERT; single self-signed device → "insecure_tls": true.
Docker host via SSH failsSSH target works? (Tentacles → SSH hosts → Test) Is the user allowed to run docker? Then svc test <host>.
No remote control sessionClaude signed in? RC_ENABLED on? Open the session in the terminal and confirm the prompts.
Cloning failscheck URL/token; private repositories need auth.type = token, SSH URLs a deploy key.
MCP server missing in Claude“Sync”, then /mcp → reconnect in Claude.
HTTP 401 shows an HTML error pagea reverse proxy (e.g. Traefik with error pages) hides the API's own message – test the token against the API directly, check the proxy's access log for the origin status.
Token works elsewhere but not hereit belongs to another instance (two installations of the same app?) or another service shares the variable – see Tokens & variables on the service page.
Approval asked for a service just enabledfixed since v0.10: the gateway re-reads its rules before it asks. Approvals for SSH commands are the host's access mode (confirm), not the network.

Roadmap

  • Claude via API (n8n & co.): start Claude jobs from outside – HTTP API with its own tokens and profiles (read-only / standard; the svc and gateway guard rails stay), wait for the result or poll a job id, structured answers via a JSON schema, an MCP endpoint (ask_claude) for n8n's MCP client; off by default.
  • Clearer access names: read / write / confirm instead of ro / rw / confirm everywhere – the old names keep working, existing files are migrated on start.
  • Export/import: configuration and templates, e.g. for a second installation or to share templates.
  • More sandbox: prompt-injection safeguards for content from services.
